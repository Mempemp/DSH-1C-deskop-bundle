# @wingsky-1/dsh-mcp-manager — локальная редакция 0.2.14

Панель управления MCP-серверами DSH: список серверов по статусу, быстрый ввод
`stdio` / `streamable-http`, импорт `mcpServers` JSON, инструменты через четыре
middleware-инструмента (`ws_mcp_search`, `ws_mcp_detail`, `ws_mcp_call`,
`ws_mcp_list`).

Плагин — работа [wingsky-1](https://github.com/wingsky-1/dsh-plugin-hub)
(MIT, © wingsky-1). Здесь лежит его опубликованный `@wingsky-1/dsh-mcp-manager@0.2.11`
(пиры — диапазон от ядра `0.2.2-rc.1` и Cordis `4.1.0`) плюс две наши правки: очередь
записи каталога инструментов и совместимость службы `mcpManager` с ядром 0.2.2-rc.3.
Имя пакета, манифест, локаль и API — апстримные; отличается только номер версии (0.2.14),
чтобы пересборку было видно отдельно от опубликованной.

## Зачем

Issue #3 в этом репозитории: на машине с 8 MCP-серверами (~300 инструментов) хост
DSH Desktop умирает с `exit 134` — `FATAL ERROR: Ineffective mark-compacts near heap
limit`. 10 падений за два дня, heap к моменту смерти 3.3–8 ГБ, в дампе — 8651 копия
JSON-каталога инструментов, каждая со своим `discoveredAt`.

Механика в апстриме:

1. `writeFileAtomic` (запись снимка каталога) сериализовала записи одного файла
   цепочкой промисов: `previous.then(() => writeOnce(file, data))`. Нагрузка
   захвачена замыканием до своей очереди — очередь держит каждую копию.
2. `persistRoot()` пишет **весь** каталог root-а (все серверы), а вызывается на каждую
   проекцию, то есть на каждое `tools/change` от хоста. Пока идёт запись, приходят
   следующие события — и каждый вызов встаёт в очередь со своей готовой строкой
   каталога (до ~2 МБ).

Замер на вырезанных функциях апстрима: 100 параллельных `persistRoot` одного root
дают 100 параллельных записей, каждая со своей копией снимка.

## Что исправлено

Дельта — в `tools/patch.mjs`, применяется к опубликованному бандлу:

1. **Очередь записи по файлу держит только последнюю нагрузку.** Слот на файл,
   ожидающие получают резолверы; пишется только актуальный снимок
   (`last-write-wins` — все текущие вызывающие пишут полный снимок файла).
2. **`persistRoot` сливает вызовы на один root.** Пока идёт цикл, новые запросы
   становятся отметкой «ещё один проход», а снимок считается внутри цикла
   (`persistRootOnce`), поэтому ожидающие не держат ничего. Заодно исчезает
   известный апстриму остаточный дефект «две параллельные проекции пишут вразнобой»:
   на root остаётся один писатель.

Что это даёт (тот же замер на нашей сборке): 100 параллельных `persistRoot` → одна
запись за раз, две записи вместо ста; в очереди записи удерживается одна нагрузка
вместо 50 при 50 подряд идущих вызовах. Память перестаёт расти вместе с числом
событий `tools/change`.

Семантика, которую правка меняет сознательно: `resolve` у `writeFileAtomic` теперь
означает «очередь слита и на диске не старее этой нагрузки», а не «на диске ровно эти
байты». Для всех текущих вызывающих (полные снимки каталога, состояния и версии) это
одно и то же.

## Служба `mcpManager` на ядре 0.2.2-rc.3

С rc.3 ядро само предоставляет службу `mcpManager` — свой менеджер MCP-серверов с
поверхностью `list` / `register` / `restart` / `probe` / `watch` (пакет
`@deepseek-ai/dsh-mcp-manager` в составе `web-app`). Наш пакет объявлял ту же службу
своим `ctx.provide("mcpManager", …)`, а Cordis на второе `provide` одного имени
бросает:

```
service "mcpManager" has been registered at <…>
```

Исключение вылетало из `apply` до регистрации маршрутов: `apply` падал целиком, ни одной
строки `/api/dsh-mcp/*` не появлялось, и каждый запрос панели (начиная с
`GET /api/dsh-mcp/servers?cwd=…`) уходил в хост ни с чем — панель показывала
`Load failed: HTTP 404`, «0 running» и пустой список.

Правка: имя занимается только если оно свободно (старая линия ядра, до rc.3). Если служба
уже есть, наши старые методы — `registerServer`, `unregisterServer`, `connect`,
`disconnect`, `reconnect`, `getStatus`, `getTools` — дописываются на службу ядра и
снимаются при выгрузке плагина; методы ядра (`list`, `register`, `restart`, `probe`,
`watch`) не подменяются никогда. Поэтому сторонние плагины, которые брали менеджер через
`ctx.get("mcpManager")` и звали `registerServer` / `reconnect` (например,
`dsh-1c-project-properties` и `dsh-engram-memory`), продолжают работать на новом ядре.

## Номер версии

Имя пакета — апстримное, номер — наш: 0.2.14 поверх опубликованной 0.2.11. Бандл берёт
версию из своего `package.json` и по ней же измеряет апгрейд-лестницу home-хранилища
(`runUpgradeChain` вызывает `diagnoseGap`), поэтому генератор дописывает в конец
лестницы пустой шаг `0.2.11 → 0.2.14` с общим `tickUpgradeVersion`. Без своего шага
последняя ступень апстрима остаётся 0.2.11, и при каждом старте плагин пишет в лог,
что хранилище отстало от версии пакета. Форма хранилища при этом не менялась.

## Сборка

```bash
node tools/patch.mjs           # пересобрать lib/ из апстрима и дельты
node tools/patch.mjs --check   # проверить, что lib/ совпадает с генератором
```

Апстрим берётся по пиннутой ссылке npm и проверяется по `sha512` архива и `sha256`
бандла; при расхождении генерация падает, а не смешивает версии. Офлайн-прогон:
`--upstream <каталог|архив>` или `DSH_MCP_MANAGER_UPSTREAM_DIR`.

Проверки поведения — в корне репозитория: `test/dsh-mcp-manager-write-queue.test.ts`
(очередь записи, подменённый диск) и `test/dsh-mcp-manager-service.test.ts` (служба
`mcpManager` в двух формах хоста). Оба теста вырезают функции из собранного
`lib/index.js`, а не проверяют копию логики рядом.

## Когда удалять

Появится релиз апстрима с исправленной очередью — переключить
`installer-flavor.yml` на опубликованный тарбол (или коммит), удалить этот каталог и
тест, оставив запись в `docs/releases/`. Дельта подготовлена так, чтобы её можно было
отправить апстриму как предложение; принимать — их решение.
