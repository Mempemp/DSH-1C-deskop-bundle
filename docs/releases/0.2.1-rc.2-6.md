# 0.2.1-rc.2-6

Каталог и установщик для ядра `0.2.1-rc.2`. Отличие от `0.2.1-rc.2-5` — только менеджер
MCP-серверов: он едет локальной редакцией с исправленной очередью записи каталога
инструментов. Остальные компоненты и пины не менялись (аудит зависимостей — в конце).

## Менеджер MCP не убивает хост по OOM

`@wingsky-1/dsh-mcp-manager` 0.2.10 писал снимок каталога инструментов так, что каждый
ждущий вызов держал свою готовую копию JSON. Каталог переписывается на каждое изменение
набора инструментов (`tools/change`), поэтому на машине с несколькими MCP-серверами
очередь росла вместе с числом событий: в отчёте пользователя — 8651 удержанный снимок,
хост падал с `exit 134` (`Ineffective mark-compacts near heap limit`) десять раз за два
дня на конфигурации 8 серверов / ~300 инструментов.

Что сделано в локальной редакции (`packages/dsh-mcp-manager`, `from: local`):

- очередь записи на файл держит только последнюю нагрузку: `last-write-wins`, ожидающие
  получают резолверы и не держат данные;
- `persistRoot` сливает параллельные вызовы на один root: пока идёт цикл, новые запросы
  становятся отметкой «ещё проход», а снимок считается внутри цикла из живого состояния.

Замер на стенде (8 серверов × 40 инструментов, ~320 инструментов — конфигурация отчёта):
физических записей каталога 7 вместо 27, итоговый файл тот же (703 КБ, 8 серверов по 40
инструментов), время до слива и память хоста не изменились.

Проверено: очередь и `persistRoot` гоняются тестами на функциях, вырезанных из собранного
бандла (`test/dsh-mcp-manager-write-queue.test.ts`), в живом хосте на отдельном профиле
плагин загружается каталогом поставки, подключает серверы и пишет каталог.

Ограничение, которое стоит знать: синтетический прогон с 2400 инструментами (8 серверов
по 300) валит хост по OOM и с этой редакцией, и с апстримом — там срабатывает другой
удерживатель, не связанный с очередью записи (до смерти успевает пройти одна запись).
Это отдельная задача; конфигурация из отчёта в неё не попадает.
