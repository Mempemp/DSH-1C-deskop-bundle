# Релиз

Релиз здесь — публикация готового установщика из форка. Сборки в этом репозитории не запускаются.

## 1. Версия

Версия принадлежит форку: `package.json` и `apps/desktop/package.json` там обязаны совпадать.
Схема — `<ядро>-<подрелиз>`, например `0.2.0-rc.2-5`. Подрелиз увеличивается на каждый выпуск,
даже если меняется только упаковка.

## 2. Сборка

```sh
# из корня клона форка; каталог берётся из клона DSH-1C-deskop-bundle рядом с форком,
# иначе путь задаётся DSH_1C_BUNDLE_ROOT
cp apps/desktop/.env.windows.1c apps/desktop/.env.windows   # один раз на клон, файл в git не входит
node apps/desktop/scripts/prepare-1c-catalog.mjs
PATH="/c/Windows/System32:$PATH" node apps/desktop/node_modules/pnpm/bin/pnpm.mjs \
  --dir apps/desktop run package:win:x64:unsigned
```

Второй вызов эквивалентен `pnpm --dir apps/desktop run package:win:x64:unsigned`, если pnpm подключён
через `corepack enable`.

Два условия запуска — оба выглядят как дефекты сборки, хотя это окружение:

- **`PATH` с `System32` впереди.** Упаковка читает манифесты паков через `tar -xOzf <путь>`, а
  первым в `PATH` из git-bash идёт GNU tar, для которого `D:\…` — это «хост D»: ошибка
  `tar (child): Cannot connect to D: resolve failed`, за ней `unexpected end of file` и падение
  `prepare:packages`. Системный `C:\Windows\System32\tar.exe` такие пути понимает.
- **Настоящий TTY на stdin и stdout.** Упаковка рисует прогресс и падает с `stdin is not a tty`
  (если stdin — не терминал) или `stdout is not a tty` (если stdout перенаправлен или идёт через
  `tee`). В фоне запускать с pty и без перенаправления вывода.


Прогоны каталога в течение одного релиза повторяются (сдвинулся пин плагина, поменялась версия),
поэтому архивы git-источников, закреплённых коммитом, кэшируются в
`%LOCALAPPDATA%\dsh-1c-catalog\downloads` — `DSH_1C_CATALOG_CACHE` для другого места. Первый прогон
после смены пина качает `dsh-web` (~800 МБ), следующие печатают `download cache hit`. Теги и ветки
не кэшируются, поэтому пин тегом стоит повторной загрузки. Подробности — в
[разработке](development.md#кэш-загрузок-каталога).

Сборка длится около 13 минут и заканчивается `success: True` в
`apps/desktop/.desktop-build/packaging-runs/<время>/result.json`. Артефакты — в
`apps/desktop/.desktop-build/targets/win-x64/unsigned-artifacts/`.

## 3. Проверки до публикации

- Первый запуск на отдельном `DSH_HOME`: каталог применён, плагины на месте, MCP-строки видны.
- Перенос данных: дом с отметкой прошлой схемы должен получить ключи и реестр папок.
- Сборку, которая меняет обработку обновлений, проверяют на реальном обновлении предыдущей версии.
- Перед запуском установщика закрыть DSH Desktop: при живом процессе мастер открывается и сразу
  выходит, ничего не установив. Проверять `Get-Process -Name 'DSH*'` — при старте приложение
  поднимает несколько процессов, одного закрытого окна недостаточно.
- Комплектный git проверяется не по установщику, а в доме: `%USERPROFILE%\.dsh\git\cmd\git.exe`
  и строка `installed tool git@` в `%USERPROFILE%\.dsh\logs\catalog-seed.log`. Каталог без
  `tools/git` теперь валит сборку (`CATALOG INCOMPLETE`, ненулевой код), но на машине с
  антивирусом копирование может упасть по EPERM — раскатка повторит попытку и назовёт элемент.
- **Страница «1С: Параметры проектов» отвечает 404 на `/1cprops/*`.** Клиент рисуется, значит плагин
  в профиле есть, а хост-часть не зарегистрировала маршруты: почти всегда в профиле два владельца
  одних и тех же маршрутов и второй `apply` упал. Проверять в
  `%USERPROFILE%\.dsh\profiles\desktop\package.json` список `dsh.profile.bundles` — ушедший
  `dsh-rlm-tools-bsl` быть не должен, и в `logs\catalog-seed.log` строки
  `uninstalled plugins the catalog no longer ships` / `dropped bundle rows`. Если строка осталась,
  раскатка не дошла до сверки: смотреть `[catalog] ... failed` в том же журнале.

## 4. Манифесты фида

В релиз кладутся четыре ассета: `.exe`, `.blockmap` и два манифеста.

| файл | версия | читатель |
| --- | --- | --- |
| `dsh1c.yml` | настоящая (`0.2.0-rc.2-N`) | текущая линия (канал `dsh1c`) |
| `latest.yml` | `0.11.0-3` | установленные `0.11.x` |

`latest.yml` — копия `dsh1c.yml` с заменённой строкой `version:`; путь, `sha512` и `size`
указывают на текущий установщик. Без него сборки `0.11.0-2` не увидят обновление: их semver
считает `0.2.x` более старым, чем `0.11.0-2`.

## 5. Публикация

Сначала — зависимости. Каталог ссылается на коммиты других репозиториев, поэтому до тега проверить,
что они запушены: форк (ветка с патчами десктопа), `Mempemp/DSH-1CProjectProperties`,
`Mempemp/DSH-CodeEditor_BSL`. Локальные плагины (`packages/*`) своего репозитория не имеют и едут
внутри бандла. Признак незапушенного: у ветки нет upstream в `git branch -vv` либо
`git rev-list --count origin/main..main` больше нуля. Установщик с пином на незапушенный sha
собирается и работает, но повторить его из GitHub уже нельзя.

```sh
git tag 0.2.0-rc.2-5 && git push origin 0.2.0-rc.2-5
gh release create 0.2.0-rc.2-5 --latest --notes-file docs/releases/0.2.0-rc.2-5.md \
  D:/.../DSH-1C-Setup-0.2.0-rc.2-5-win-x64-unsigned.exe \
  D:/.../DSH-1C-Setup-0.2.0-rc.2-5-win-x64-unsigned.exe.blockmap \
  D:/.../dsh1c.yml D:/.../latest.yml
```

- Тег — **без** префикса `v`.
- Релиз обычный, не pre-release: `releases/latest/download/` работает только для таких.
- `gh` — нативная программа: пути передавать в виде `D:/...`, иначе не найдёт файл.
- В `gh release create` суффикс `#имя` — это метка, а не имя ассета: файл должен называться
  буквально `latest.yml`.

## 6. Проверка после публикации

```sh
curl -sL https://github.com/Mempemp/DSH-1C-deskop-bundle/releases/latest/download/dsh1c.yml | head -3
curl -sL https://github.com/Mempemp/DSH-1C-deskop-bundle/releases/latest/download/latest.yml | head -3
```

Первая строка — новая версия, вторая — `0.11.0-3` с путём на тот же установщик.

Локальная сверка до загрузки не ловит перепутанные вложения, поэтому после публикации скачать
манифесты из самого релиза и сравнить с файлом:

```sh
cd /tmp && rm -rf relchk && mkdir relchk && cd relchk
gh release download <тег> --pattern "*.yml"
grep -E "^version:|^path:|sha512|size:" dsh1c.yml latest.yml
```

`sha512` и `size` в обоих файлах должны совпадать с установщиком, `dsh1c.yml` нести версию сборки,
`latest.yml` — версию линии (`0.11.0-N`) и путь на тот же файл.

Промежуточные сборки удаляются сразу после выхода рабочей версии, чтобы их нельзя было поставить
случайно: `gh release delete <тег> -y` и `git push origin --delete <тег>`.

## 7. Уборка после релиза

Сборочный каталог копится сам, и это не мусор «сам по себе», а отсутствие шага уборки: каждый
прогон оставляет ~400 МБ установщика, ~1,2 ГБ распакованного `win-unpacked` и каталог прогона с
логами. За неделю сборок набегает несколько гигабайт, и найти среди них актуальный файл уже
непросто.

Держим в `apps/desktop/.desktop-build/targets/win-x64/unsigned-artifacts` **два установщика** —
текущий и предыдущий опубликованный (он нужен, чтобы проверить обновление с прошлой версии). Всё
остальное там — либо опубликовано на GitHub, либо уже не воспроизводится:

```sh
# оставить текущую и предыдущую версии, остальные .exe/.blockmap убрать
ls DSH-1C-Setup-*-win-x64-unsigned.exe | sort -V | head -n -2 | xargs -r rm -f
```

Осторожно с **неопубликованными** сборками: если версия не уходила в релиз, её `.exe` здесь
единственная копия. Перед удалением сверить с `gh release list` — опубликованное живёт на GitHub,
неопубликованное живёт только тут.

Второе место — кэш апдейтера, `%LOCALAPPDATA%\dsh-desktop-updater`:

- `installer.exe` — скачанный установщик прошлого обновления, ~400 МБ; приложению не нужен, оно
  скачает заново.
- `pending/` — **скачанное, но не применённое обновление**. Оно применяется при следующем старте,
  поэтому старый `pending` способен неожиданно откатить установку на прошлую версию. Если на
  машине ставится свежая сборка руками, `pending` удалять до её запуска.

Третье — локальные архивы плагинов `$DSH_HOME/dev-plugins`: они остаются после каждой локальной
установки «без сборки» (по ~6 МБ на версию). Хранить имеет смысл только те версии, что стоят в
профиле сейчас.
