# Переезд сборки «DSH для 1С» на официальный десктоп DeepSeek Harness

Статус: **план, ничего не реализовано**. Факты ниже проверены 2026-10-01 на живых URL и
исходниках апстрима; всё, что не проверено, помечено явно.

## 1. Куда переезжаем

Официальный десктоп — не отдельный проект, а часть монорепозитория
`deepseek-ai/deepseek-harness` (MIT, ветка `master`, ~20 тыс. коммитов):

| Путь | Что это |
| --- | --- |
| `apps/desktop` | Electron-оболочка: `src/main.ts`, трей, крэш-логи, welcome-окно, quit-инспекция задач, свой NSIS-инсталлятор (`installer/*.nsh`), `electron-updater` |
| `apps/desktop-host` | `@deepseek-ai/dsh-desktop-host` — приватный (`private: true`) Node-хост, крутит dsh в Electron RunAsNode |
| `apps/cli`, `apps/web`, `packages/*` | ядро, веб-UI, менеджер плагинов |

Ключевые свойства:

- **Версия оболочки = версия ядра.** `apps/desktop/package.json` — `0.2.0-rc.2`, `@deepseek-ai/dsh`
  тот же. Релиз десктопа = релиз ядра (release identity), отдельного номера у оболочки нет.
- **Дом — общий `$DSH_HOME`** (`~/.dsh`, `packages/util/home-paths/src/index.ts`), профиль
  `profiles/desktop` (`apps/desktop/src/paths.ts`). Сессии, настройки, ключи, воркспейсы общие с CLI,
  `node_modules` и локи — нет.
- **Ядро едет в поставке**: `app.asar/dsh` несёт полное production-дерево; при первом запуске ничего
  не доустанавливается. Плагины ставит встроенный pnpm 11.7 в профиль `desktop` через общий
  веб-менеджер плагинов (`packages/boot/plugin-manager`).
- **В комплекте**: Python + Node + pnpm (`load_workspace_dependencies`, `~/.dsh/dsh-runtimes/…`),
  office-скиллы, меню «Manage dsh Command» (ставит `dsh` в PATH пользователя).
- **Обновления** (проверено запросом): generic-фид, канал `nightly`,
  `https://download.deepseek.com/dsh-desk/feeds/win-x64/nightly.yml` → 200,
  версия `0.2.0-rc.2`, артефакт `deepseek-harness-0.2.0-rc.2-win-x64.exe`,
  size 289 313 640, sha512 совпадает с `download.deepseek.com/desktop/dsh-latest-windows-x64.exe`.
  Для mac — `nightly-mac.yml`.
- **Раскладка фида и mandatory-policy зашиты при сборке** из `apps/desktop/.env.windows`:
  `DSH_DESKTOP_AUTO_UPDATE_ENV=test` → обязателен свой `DOWNLOAD_TEST_ORIGIN` + 32-символьный
  `DOWNLOAD_TEST_RELEASE_ID`; `production` → origin **жёстко** `https://download.deepseek.com`.
  Путь: `<origin>/dsh-desk[/<id>]/feeds/<target>/`. Policy — `<origin>/api/v0/check_client_update`
  (no-force = `{code:0,biz_code:0,biz_data:null}`), origin обязателен даже для unsigned-сборки.
- **Чего в апстриме нет вообще**: офлайн-каталога и сидинга плагинов при установке, «генераций»
  (это дизайн стороннего dsh-desktop), русского языка оболочки (Electron-строки только en/zh,
  фолбэк английский), своего канала обновлений, выбора папки установки под нас.
- Известные ограничения самого апстрима: вход в аккаунт не подключён (кнопка Sign in disabled),
  релизная подпись/нотаризация/хостинг обновлений требуют их релизного окружения.

## 2. Что у нас сейчас (база сравнения)

- База `dataelement/dsh-desktop` v0.11.0 (03.10.2026) → ядро `@deepseek-ai/dsh` **0.2.0-rc.2**:
  база обновлена 04.10.2026, отставания по core-минору больше нет.
- Свой дом `%APPDATA%\dsh-desktop\harness`, плагины — **генерациями**
  (`profiles/.generations/desired.json`), наш `packages/dsh-desktop-market-installer`.
- Наш слой: ~30 файлов `src/main`, 36 файлов `src/main/state` (генерации, `installer-catalog-seed`,
  `market-baseline`, миграции), `src/main/update/*`, 9 своих пакетов, 122 теста.
- Каталог: 15 источников (13 плагинов, 1 MCP, 1 payload), офлайн-сид из инсталлятора,
  свой фид обновлений на GitHub Releases (4 вложения), русская оболочка, свой инсталлятор.

Харнесс-половина (каталог, плагины 1С, MCP, скиллы, payload) живёт в **профиле**, а не в Electron —
поэтому она переносится почти как есть; разница целиком в Electron-слое и в том, кто владеет
профилем и обновлениями.

## 3. Маршрут

Рекомендация: **этап 1 — надстройка без форка**, форк — второй этап за гейтом (см. §6).

| Требование | Без форка | С форком |
| --- | --- | --- |
| Авто-установка плагинов/MCP/скиллов/payload из каталога | да (их CLI + наш сид) | да |
| Офлайн, без npm-registry | да (`bundleDependencies` в наших тарболах) | да, ещё чище (bundle в поставке) |
| Русский продукт (веб-UI) | да (плагин `russian-lang`) | да |
| Русская оболочка (инсталлятор, welcome, меню, карточки обновлений, трей, диалог восстановления) | **нет** — строки в Electron-бандле | да, ~3–4 файла оверлея |
| Свой канал обновления приложения | **нет** — origin апдейтера зашит, `app-update.yml` править нельзя (инвентарь `desktop-runtime.json` сверяется при старте) | да |
| Трей, инспекция задач, крэш-логи, встроенные рантаймы, office | да, от апстрима | да |

### Открытые решения (нужен ответ пользователя)

1. **Русская оболочка.** Это единственное, что действительно требует форка.
   - (A) Принять английские углы, продукт и каталог русские; форк — запасной вариант. *(рекомендуется)*
   - (B) Пилот без форка на 1–2 машинах, решение по форку по итогу.
   - (C) Форкать сразу.
2. **Автообновление приложения.** Их фид обновляет shell+ядро+pnpm одним подписанным юнитом —
   это лучше нашего канала. Варианты: (A) принять их фид, наш канал оставить для каталога
   *(рекомендуется)*; (B) приложение обязано обновляться нашим каналом → только форк.
3. Перенос данных существующих установок (`%APPDATA%\dsh-desktop\harness` → `~/.dsh`) —
   отдельный пункт плана, решение не принято.

## 4. Этап 0 — совместимость каталога с ядром 0.2.0-rc.2 (выполнено при обновлении на v0.11.0)

Каталог собран под 0.1.7-rc.2 и переведён на 0.2.0-rc.2 вместе с базой v0.11.0. Апстрим проверяет `peerDependencies` каждого плагина на
`@deepseek-ai/dsh*` против единственной версии рантайма (`packages/boot/app-boot`), а несовместимый
peer **отклоняет установку до pnpm** и на старте выключает строку.

1. Снять факт: для каждой из 13 позиций каталога — `peerDependencies` из тарбола против
   `node_modules/@deepseek-ai/*` установленного официального приложения.
2. Обновить плагины до версий, которые апстрим называет для 0.2.x (не `latest`: диапазон может
   численно принимать нашу версию, а код звать исчезнувший метод).
3. Прогнать наш скан на формы источника сообщений старого вида (ядро 0.1.7+ пишет сессии как v4 и
   отвергает `{kind:'plugin', plugin:…}` на записи).
4. Обновить MCP-половину (`dsh-rlm-tools-bsl`, `engram`) и payload, проверить `allowBuilds` для
   нативных сборок — у официального десктопа **своего диалога одобрения build-скриптов нет**,
   зависимости с lifecycle-скриптами требуют записи в `pnpm-workspace.yaml` профиля.
5. Проверка: установка в чистый профиль официального приложения (одноразовый `DSH_HOME`) и запуск.

**Результат проверки (04.10.2026, база v0.11.0):**

- Пиры каталога против установленного ядра `0.2.0-rc.2` — чисто: `dshmarket` 1.66.8,
  `mcp-manager` 0.2.8, `modsearch` 5.10.5 (пиров нет), `better-sidebar` 0.24.1 (`^0.2.0-rc.1`),
  `skill-explorer` 0.4.4 (`@deepseek-ai/dsh >=0.2.0-rc.1`), `archify` 0.1.0 (пиров нет),
  `russian-lang` 0.3.34, `univer-office` 0.3.6; наши `1c-project-properties` 0.6.4,
  `rlm-tools-bsl` 0.1.7 и `engram` 0.1.4 несут только `@deepseek-ai/cordis` (ядро ставит 4.0.4).

**Сверка пинов перед сборкой 0.11.0-2 (15.10.2026):** подняты `dshmarket` 1.66.8 → 1.66.22
(вместе с `VERIFIED_MARKET_BASELINE` и `RECOMMENDED_MARKET_VERSION` — эти три всегда едут парой),
`mcp-manager` 0.2.8 → 0.2.9 (коммит `97cc69f`, возвращает сохранение конфигурации на Windows и
защищает внешние правки), `modsearch` 5.10.5 → 5.10.6, `better-sidebar` v0.24.1 → v0.26.0
(хостовые пиры `^0.2.0-rc.2`), `skill-explorer` 0.4.4 → 0.4.6 (пир `@deepseek-ai/dsh >=0.2.0-rc.2`),
`archify` 0.1.0 → 1.0.0 (состав tarball проверен: `skills/archify/**` и `lib/index.js` на месте),
`russian-lang` 0.3.34 → 0.3.45 (пир `dsh-settings ^0.2.0-rc.2`), `univer-office` 0.3.6 → 0.3.7,
`dsh-bsl-editor` 0.5.3 → v0.6.2 (`d65be2f`), payload `1c-rules` → коммит `96c4d96`. Без изменений:
`1c-project-properties` 0.6.5, `rlm-tools-bsl` 0.1.8, `engram` 0.1.5. База — по-прежнему **v0.11.0**:
у апстрима с 09.10.2026 лежит v0.11.1, но её пин ядра тот же (`0.2.0-rc.2`), и перенос базы —
отдельная работа, а не часть этой сборки.
- `dsh-bsl-editor` 0.5.3: из ядра убран `@deepseek-ai/dsh-client-runtime` (последняя публикация —
  0.1.1-rc.2), а плагин держал его и пиром, и в `dsh.client.inject`; снято, три хостовых пира

- Не проверено: `allowBuilds` для нативных зависимостей в `pnpm-workspace.yaml` профиля (пункт 4)
  и установка в чистый профиль официального приложения (пункт 5) — это отдельный маршрут, не наш
  бандл.

## 5. Этап 1 — надстройка без форка

Что делаем:

1. **Стенд.** Официальное приложение запускается с переменной `DSH_HOME` на временный каталог —
   рабочий `~/.dsh` не трогается. Это единственный дешёвый способ прогонять сценарии сидинга и
   обновлений, не ломая рабочую среду.
2. **Бутстраппер (наш новый установщик).**
   - ставит официальный инсталлятор (у него есть silent-режим — в апстриме это проверяется тестом
     `apps/desktop/scripts/test-windows-installer.mjs`);
   - запускает приложение, ждёт появления `$DSH_HOME/profiles/desktop/package.json`
     (**профиль инициализирует только само приложение** — CLI отказывается создавать
     десктоп-профиль, `.agents/notes/implemented/feature/2026-09-27-desktop-cli-runtime.md`);
   - гасит приложение (профиль занимается эксклюзивно, пока приложение живо; на пустом профиле
     выход без диалогов);
   - заливает каталог их же CLI: `resources/runtime/cli/bin/dsh.cmd plugin --profile desktop add <…>`
     по абсолютным путям к нашим `.tgz` (встроенный pnpm и согласование `dsh.profile.bundles`
     приезжают вместе с обёрткой);
   - запускает приложение для пользователя.
   - Отвергнутая альтернатива: самим создать файлы профиля (`package.json` c
     `@deepseek-ai/dsh-desktop-runtime` + `dsh.profile.bundles`, `pnpm-workspace.yaml`, `lock`).
     Формат приватный и версионно-связанный (`apps/desktop/src/project-manager.ts`), ошибка даёт
     «required plugin did not activate» на старте. Не делаем.
3. **Сид.** 13 плагинов tarball'ами + MCP-строки (наши плагины регистрируют сервер сами) + payload
   и скиллы + `allowBuilds`. Офлайн — за счёт `bundleDependencies`.
4. **Наш канал для каталога.** Маленькая проверка версии ядра при старте бутстраппера: при смене
   версии приложения (их апдейтер обновит его сам) — перепин/переустановка каталога, потому что
   peer-диапазоны привязаны к версии ядра.
5. **Что умирает вместе с dsh-desktop:** `src/main/state/*` (генерации, `installer-catalog-seed`,
   миграции), `src/main/update/*`, `packages/dsh-desktop-market-installer`,
   `packages/dsh-desktop-log-bridge`, `packages/dsh-desktop-hmr-fallback`. Переезжают как профильные
   плагины: `dsh-image-generation`, `dsh-notifier-ru`, `dsh-plugin-gis`,
   `dsh-desktop-preset-transfer`, `dsh-desktop-client-ui`.

## 6. Этап 2 — форк (только если английские углы не устроят)

Гейт: неделя-две использования этапа 1 на живых машинах. Если углы мешают — тонкий оверлей на
`apps/desktop`:

- русские строки оболочки (`installer/strings.nsh`, `src/locale.ts`, welcome-окно);
- `publish` апдейтера → наши GitHub-релизы (как сейчас, provider `generic`);
- mandatory-policy выключить в оверлее (иначе нужен свой HTTPS-origin с заглушкой
  `/api/v0/check_client_update`);
- каталог — bundle'ами в поставке (`app.asar/dsh`, резолв «installation first»), без pnpm на машине;
- брендинг: `BRAND_GUIDELINES.md` запрещает использовать полное имя «DeepSeek Harness» как название
  проекта — продукт остаётся «DSH для 1С».

Цена, которую надо принять осознанно: форк **всего монорепо** (у `apps/desktop` зависимости
`workspace:*` и приватный `dsh-desktop-host`; выдернуть его отдельно нельзя), сборка `tsc -b` +
tsdown + `native/system` + `prepare:primary-runtime` (сотни МБ загрузок), артефакт ~400 МБ,
ребейз оверлея на теги апстрима (релизы каждые несколько дней), Windows-сборка без подписи
(`package:win:x64:unsigned` существует).
