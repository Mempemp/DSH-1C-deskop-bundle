# Переезд сборки «DSH для 1С» на официальный десктоп DeepSeek Harness

Статус: **план, ничего не реализовано**. Факты ниже проверены 2026-10-01 на живых URL и
исходниках апстрима; всё, что не проверено, помечено явно.

## 1. Куда переезжаем

Официальный десктоп — не отдельный проект, а часть монорепозитория
`deepseek-ai/deepseek-harness` (MIT, ветка `master`, ~20 тыс. коммитов):

| Путь | Что это |
| --- | --- |
| `apps/desktop` | Electron-оболочка: `src/main.ts`, трей, крэш-логи, welcome-окно, quit-инспекция задач, свой NSIS-инсталлятор (`installer/*.nsh`), `electron-updater` |
| `apps/desktop-host` | `@deepseek-ai/dsh-desktop-host` — приватный (`private: true`) Node-хост, крутит dsh в Electron RunAsNode |
| `apps/cli`, `apps/web`, `packages/*` | ядро, веб-UI, менеджер плагинов |

Ключевые свойства:

- **Версия оболочки = версия ядра.** `apps/desktop/package.json` — `0.2.0-rc.2`, `@deepseek-ai/dsh`
  тот же. Релиз десктопа = релиз ядра (release identity), отдельного номера у оболочки нет.
- **Дом — общий `$DSH_HOME`** (`~/.dsh`, `packages/util/home-paths/src/index.ts`), профиль
  `profiles/desktop` (`apps/desktop/src/paths.ts`). Сессии, настройки, ключи, воркспейсы общие с CLI,
  `node_modules` и локи — нет.
- **Ядро едет в поставке**: `app.asar/dsh` несёт полное production-дерево; при первом запуске ничего
  не доустанавливается. Плагины ставит встроенный pnpm 11.7 в профиль `desktop` через общий
  веб-менеджер плагинов (`packages/boot/plugin-manager`).
- **В комплекте**: Python + Node + pnpm (`load_workspace_dependencies`, `~/.dsh/dsh-runtimes/…`),
  office-скиллы, меню «Manage dsh Command» (ставит `dsh` в PATH пользователя).
- **Обновления** (проверено запросом): generic-фид, канал `nightly`,
  `https://download.deepseek.com/dsh-desk/feeds/win-x64/nightly.yml` → 200,
  версия `0.2.0-rc.2`, артефакт `deepseek-harness-0.2.0-rc.2-win-x64.exe`,
  size 289 313 640, sha512 совпадает с `download.deepseek.com/desktop/dsh-latest-windows-x64.exe`.
  Для mac — `nightly-mac.yml`.
- **Раскладка фида и mandatory-policy зашиты при сборке** из `apps/desktop/.env.windows`:
  `DSH_DESKTOP_AUTO_UPDATE_ENV=test` → обязателен свой `DOWNLOAD_TEST_ORIGIN` + 32-символьный
  `DOWNLOAD_TEST_RELEASE_ID`; `production` → origin **жёстко** `https://download.deepseek.com`.
  Путь: `<origin>/dsh-desk[/<id>]/feeds/<target>/`. Policy — `<origin>/api/v0/check_client_update`
  (no-force = `{code:0,biz_code:0,biz_data:null}`), origin обязателен даже для unsigned-сборки.
- **Чего в апстриме нет вообще**: офлайн-каталога и сидинга плагинов при установке, «генераций»
  (это дизайн стороннего dsh-desktop), русского языка оболочки (Electron-строки только en/zh,
  фолбэк английский), своего канала обновлений, выбора папки установки под нас.
- Известные ограничения самого апстрима: вход в аккаунт не подключён (кнопка Sign in disabled),
  релизная подпись/нотаризация/хостинг обновлений требуют их релизного окружения.

## 3. Маршрут

**Решение принято: форкаем официальный десктоп.** Обновлять приложение их фидом нельзя: ядро
(и контракт для плагинов) уходит вперёд само, каталог остаётся на прежнем контракте, и поломка
приезжает пользователю без нашего участия — это тот же класс, что мы уже проходили. В форке
версия оболочки равна версии ядра, значит пинится **одна комбинация «ядро + каталог»**, и апдейт
ядра выходит только после того, как каталог на ней прогнан. Обновления приложения — наш канал.

Что форк **не** решает (честно): гонку плагинов за контрактом ядра. Она остаётся, но перестаёт
быть неожиданной — ребейз на тег апстрима обязан включать прогон каталога, иначе мы своими руками
сделаем то же, что сегодня делает их фид.

Цена, которую принимаем осознанно: форк **всего** монорепо (у `apps/desktop` зависимости
`workspace:*` и приватный `dsh-desktop-host`, отдельно не выдернуть), сборка монорепо на нашей
машине, ребейз оверлея на теги апстрима, Windows-сборка без подписи.

| Требование | Без форка | С форком |
| --- | --- | --- |
| Авто-установка плагинов/MCP/скиллов/payload из каталога | да (их CLI + наш сид) | да |
| Офлайн, без npm-registry | да (`bundleDependencies` в наших тарболах) | да, ещё чище (bundle в поставке) |
| Русский продукт (веб-UI) | да (плагин `russian-lang`) | да |
| Русская оболочка (инсталлятор, welcome, меню, карточки обновлений, трей, диалог восстановления) | **нет** — строки в Electron-бандле | да, ~3–4 файла оверлея |
| Свой канал обновления приложения | **нет** — origin апдейтера зашит, `app-update.yml` править нельзя (инвентарь `desktop-runtime.json` сверяется при старте) | да |
| Трей, инспекция задач, крэш-логи, встроенные рантаймы, office | да, от апстрима | да |

### Решения

1. **Форк — да.** Причина: управлять совместимостью и стабильностью самим, а не жить на их фиде. *(решено)*
2. **Канал обновления приложения — наш.** `publish` в форке переводится на наши GitHub-релизы
   (provider `generic`, как в текущей сборке). *(решено)*
3. Перенос данных существующих установок (`%APPDATA%\dsh-desktop\harness` → `~/.dsh`) —
   отдельный пункт, решение не принято.

2. Обновить плагины до версий, которые апстрим называет для 0.2.x (не `latest`: диапазон может

## 5. Этап 1 — форк официального монорепо

База: тег апстрима `dsh-v<версия ядра>` (на момент плана — `dsh-v0.2.0-rc.2`). Форкается **весь**
монорепо; наш слой — оверлей поверх `apps/desktop` и конфига сборки, остальное не трогаем.

**Точка базы зафиксирована:** тег `dsh-v0.2.0-rc.2`, коммит `639ed015397290b3745d163aafe02ffee4aa3f84`
(29.09.2026), дерево `D:\dsh-harness\deepseek-harness` (клон `--depth 1 --single-branch`, 182 МБ).
Окружение сборки: Node 24.15.0 (их `engines` — `^22.19.0 || >=24`), pnpm **11.7.0** их пин
`packageManager` (глобальный pnpm на машине 11.0.8, corepack сломан → запускаем `npx pnpm@11.7.0`).
Гейт «`install` → `build` → `package:win:x64:unsigned`» — прогон в работе, результат дописывается сюда.

**Результат гейта (16.10.2026, машина сборки):**
- `pnpm install --frozen-lockfile` — **ОК** (~4 мин, 1392 пакета, `node_modules` 826 МБ).
- `pnpm run build` — **ОК** (client-бандлы, 347 артефактов; без MSVC, только Node/tsdown/vite).
- `package:win:x64:unsigned` — **падает** на preflight `apps/desktop/scripts/desktop-toolchain-preflight.ts`:
  `vswhere: ProgramFiles(x86) is not set…` → реальная причина: **Visual Studio C++ build tools не
  установлены** (`vswhere.exe` отсутствует). Их кастомный NSIS-инсталлятор компилирует нативный
  helper (`installer/window-frame.cpp`, extract), поэтому preflight требует компонент
  `Microsoft.VisualStudio.Component.VC.Tools.x86.x64` **для любого режима упаковки**, включая
  `--dir` и `--unsigned` (`package-target.ts:363` — шаг `toolchain` идёт до `windows-package`,
  флага «пропустить» нет).
- Отдельно: в git-bash `ProgramFiles(x86)` в окружение не попадает (имя с круглыми скобками) —
  даже с установленной VS упаковку надо запускать так, чтобы переменная была видна (cmd/PowerShell
  или подстановка через `env 'ProgramFiles(x86)=C:\Program Files (x86)'`).
- Следствие для плана: VS Build Tools — обязательное требование **сборочной машины** (и любого
  раннера: у `windows-latest` в GitHub Actions он предустановлен). Код и оверлей это не затрагивает.

Проверка без упаковки (MSVC не нужен): `pnpm run start:desktop` — собирает одноразовый проект и
запускает Electron из уже собранных артефактов, дев-профиль `apps/desktop/.desktop-build/development/home`,
рабочий `~/.dsh` не трогается. При первом запуске докачивает primary-runtime (Python/Node payload).

1. **Форк и сборка.** Клон, наш remote, сборка их же цепочкой: `pnpm install`, `pnpm run build`,
   затем `package:win:x64:unsigned` (`apps/desktop/scripts/package-target.ts`). Нужны Node 22.19+/24,
   pnpm 11.7 (пин в `packageManager`), загрузка `prepare:primary-runtime` (Python/Node/pnpm payload,
   `scripts/primary-runtime/lock.json`). Первый прогон — на временном `apps/desktop/.desktop-build/`,
   рабочий `~/.dsh` не трогается.
2. **Оверлей — что именно правим в `apps/desktop`:**
   - русские строки оболочки: `installer/strings.nsh` (+ `pages.nsh`, `lifecycle.nsh`),
     `src/locale.ts`, welcome-окно (`src/client/*`);
   - `publish` → наши GitHub-релизы: `scripts/electron-builder-config.mjs` (`provider: 'generic'`,
     url наших релизов, свой канал) плюс адрес фида в нашем апдейтере;
   - mandatory-update policy в оверлее выключается (иначе нужен свой HTTPS-origin с заглушкой
     `/api/v0/check_client_update` — origin обязателен при упаковке даже для unsigned);
   - каталог 1С — **bundle'ами в поставке**: плагины/скиллы/MCP кладутся в дерево `app.asar/dsh`
     и описываются слоем профиля, без pnpm и реестра на машине пользователя. Это тот же механизм,
     которым апстрим возит office-скиллы и `OPTIONAL_BUNDLES`;
   - брендинг: `BRAND_GUIDELINES.md` запрещает полное имя «DeepSeek Harness» как название проекта —
     продукт остаётся «DSH для 1С».
3. **Версии и политика.** Версия сборки = версия ядра + наш счётчик (`0.11.0-N`), как сейчас. Ребейз
   оверлея на новый тег апстрима **не считается готовым** до прогона каталога на новой комбинации:
   peer-контракты, формат сессий, API менеджера плагинов. Ради этого форк и делается.
4. **Что умирает вместе с dsh-desktop:** `src/main/state/*` (генерации, `installer-catalog-seed`,
   миграции, `market-baseline`), `src/main/update/*` (свой апдейтер переписывается под их
   `update-coordinator`), `packages/dsh-desktop-market-installer`, `packages/dsh-desktop-log-bridge`,
   `packages/dsh-desktop-hmr-fallback`. Переезжают как bundle'ы поставки: `dsh-image-generation`,
   `dsh-notifier-ru`, `dsh-plugin-gis`, `dsh-desktop-preset-transfer`, `dsh-desktop-client-ui`.

## 6. Отвергнутая схема: надстройка без форка

Не берём: приложение обновлялось бы их фидом, ядро уходило бы вперёд без нашего участия, каталог
оставался бы на прежнем контракте — тот самый рассинхрон, из-за которого уже падали сборки.
Остаётся в плане только как справка, если понадобится быстрый стенд:

- профиль `profiles/desktop` инициализирует **только само приложение**
  (`apps/desktop/src/project-manager.ts` → `initProfile`); CLI отказывается создавать
  десктоп-профиль (`.agents/notes/implemented/feature/2026-09-27-desktop-cli-runtime.md`) —
  сид возможен лишь после первого запуска и при закрытом приложении (профиль занят эксклюзивно);
- их CLI (`resources/runtime/cli/bin/dsh.cmd plugin --profile desktop add <…>`) несёт встроенный
  pnpm и согласование `dsh.profile.bundles` — это единственный поддерживаемый путь записи в профиль;
- писать файлы профиля самим нельзя: формат приватный и версионно-связанный, ошибка даёт
  «required plugin did not activate» на старте.

## 7. Риски

| Риск | Как проверяем |
| --- | --- |
| Плагин каталога несовместим с ядром | прогон каталога на комбинации «ядро + каталог» до тега |
| Мы сами задержим ребейз и отстанем от апстрима | держим короткий срок «тег апстрима → наша сборка»; отставание видно по номеру ядра в сборке |
| Ребейз уедет без прогона каталога | правило релиза: комбинация проверяется ДО тега, а не после |
| Сборка монорепо не встанет на нашем окружении (payload, native, unsigned) | первый полный `package:win:x64:unsigned` — до любых правок оверлея |
| Пользователь с уже установленной сборкой | решение открыто (см. §3.3) |

## 8. Не проверено

- Подпись официального Windows-инсталлятора (файл 289 МБ не качался).
- Поведение их CLI на наших `.tgz` живьём — не запускалось; ожидания выведены из исходников
  CLI-обёртки и менеджера плагинов.
- Silent-установка их NSIS и поведение завершения приложения на пустом профиле — по коду и тестам
  апстрима, не воспроизводилось.
